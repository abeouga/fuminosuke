## 1. 確認した問題

`20261013-luna-effort/L01`（low）と`L03`（none）の原応答を再確認しました。lowは22個、noneは23個のvalue宣言を出し、**すべてlabels=[]、axis=direct**です。点検表の必要な横18組・氏名/日付の縦2組はどちらも0/20でした。noneの23宣言は保留前の数であり、適用可能な23欄という意味ではありません。既存の矛盾分離後に残ったvalueは2個です。

原因は次の境界にあります。

- `visual_provider.py::INSTRUCTIONS`は各欄の名前を要求しますが、見出しセルを持つ場合にも直接指定を許します。
- `visual_answer.py::DirectValue`は空のlabelsを正当な表現として認めます。これは実際に見出しがない欄には必要です。
- `graph.py::validate_graph`は参照・役割・所有・親循環等を検査しますが、画像上の見出しを見落としたことまでは証明できません。
- `visual_pack.py::build_model_pack`は物理行列候補を渡す一方、一般フォームの接続候補は渡していません。
- 独立したlabels/ignored/headings/valuesへの重複宣言は、同じセルの矛盾を生みます。現行の部分保留は被害を限定しますが、認識品質を修復しません。

したがって、画面だけの修正では解決できません。変更対象はテンプレート解析の候補入力と回答契約です。通常の記入済み帳票OCR、値の認識、補正、出力処理は対象外です。

## 4. 候補カタログ

新しい`visual_bindings.py`に、IOとDBを持たない候補生成を置きます。元の画像や矩形を修正せず、`VisualEvidence.metadata_json`のセルを使います。

- 各候補は`ref / input / label / axis`を持ちます。短い`b1`等の参照は、その要求のカタログdigestにだけ有効です。別の要求へ持ち越せる永続IDではありません。
- 最初に、辺の隔たり2px以内、直交方向の重なりが短い辺の50%以上の組を、左右・上下の両向きで列挙します。向きは意味ではなく候補です。候補順は数値セル参照・軸・座標で固定します。
- 余白で離れた欄には、同じ投影重なり条件で各方向の最短非負距離の候補を追加します。同距離はすべて残します。接触候補を置き換えません。中間セルや距離も候補の根拠として保存します。最短候補が正解とは扱いません。
- 既存の明示relationは別途保持し、距離による候補外しをしません。保護された入力は書込候補にしません。読取専用セルを見出しとして使えるのは、現在のlabel役割とfacet保護に反しない場合だけです。
- 未固定の検出roleや未検証textHintでは候補を落としません。親候補との直積は作らず、親は画像中の発行済みセルから別に選びます。
- 複数見出しは複数の候補参照を同時選択して表現します。すべて同じinput・同じaxisでなければ保留します。重複、自己参照、入力と見出しの兼用を許しません。
- 初期上限は1作業単位4096候補、候補metadata 64KiBとします。超過時に末尾を切り捨てたり近い順に採用したりせず、その単位を送信前保留します。候補不足も評価上の失敗に数えます。この上限は実装時の開発5ページ診断で適否を確認します。
- 検出済みセルの無い印字、斜めや離れた複合対応、別ページの対応は、この候補だけでは保証できません。候補外を明示して保留し、矩形修正または後続の入力設計へ戻します。自由なID・座標を回答へ混ぜて通しません。

今回、R02定期点検の接触候補だけを意味推測なしで列挙した診断では、204候補に必要な20組すべてが含まれました。候補表の追加量は4,929文字です。これは候補到達性であり、AIが正しく選べる証拠ではありません。氏名/日付以外の非接触欄、複合ラベル、他帳票の網羅性はまだ未検証です。

`c49`は`c50`に接触していますが、c49は自由記入欄であり印字ラベルではありません。この例を「隣ならlabel」とする誤実装の負例に固定します。

## 5. 回答契約 `template-analysis.form.v1`

要求名を`template_visual_form`に固定します。rootはobject、全propertyはrequired、nullableは明示、各objectは追加property禁止とします。unionは配列要素などの内側で使います。これはOpenAI Docsの[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)に合わせた形です。対応したschemaでも実送信の受入確認は別に必要です。

rootは`version / readings / groups / headings / annotations / tables / unresolved`です。

| 部分 | 宣言する内容 |
| --- | --- |
| readings | 現行Readingを再利用。記号の選択肢、実際の凡例文、根拠セル。枠外凡例の空evidenceRefsを維持 |
| groups | 共通parentとreadingを1回指定し、fieldsを列挙。グループは伝送上の共通値であり、別欄の意味IDや保存先を共有させない |
| linked field | `kind=linked / links=[b参照...] / name`。入力・ラベル・軸を候補から一意に展開。nameはAIが画像から判断 |
| unlabelled field | `kind=unlabelled / cell / name / evidence`。evidenceは`basis=free_entry又はin_cell_caption / text / refs`を必須とし、画像上の根拠を明示 |
| headings | 現行VisualHeading。名称、親、セルを一体で指定。parentがこの回答の新規見出しなら宣言必須 |
| annotations | 意味付けに使わないセルのlabel/ignored/record_key/column_keyだけ。入力・mark・parent_labelを別宣言できない |
| tables | 現行ExplicitTableを維持。不規則な表の明示行列と空行を省略しない。groupsとの二重所有は拒否 |
| unresolved | 候補なし、曖昧な対応、根拠不足などを対象セル付きで宣言。public reasonは現行IssueReasonへ明示対応 |

候補不足をunlabelledへ読み替えません。`free_entry`は親分類や欄内・周囲の具体的な視覚根拠が必要です。単に「ラベルがない」という同義反復を根拠にしません。枠外印字の物理接続が必要なのに未検出なら`missing_binding`又は`missing_evidence`として保留します。

ただし、根拠文を必須にしてもAIの虚偽の見出しなし判定を機械的に証明できるわけではありません。候補が存在するunlabelled案は、画面の既存detailsにも「見出し接続なし」と根拠を示し、人間が訂正できるようにします。20組のラベルを省略した案は評価で不合格です。schemaの巧妙化だけで精度問題が消えたとは扱いません。

`annotations`はlinked fieldから導かれるlabelを重複して書く場所ではありません。同じセルの別役割・別親は現行と同じ依存成分保留の対象です。余ったセルをサーバーが勝手にignoredへ変えません。省略は未解決です。

## 6. 展開と保護

`visual_form_answer.py`は型の検査と、要求で固定した候補を使う決定的な展開だけを担当します。providerは要求したschema名からparserを選び、失敗後に他形式を試しません。

1. 全回答の候補ID・セルID・reading参照を検査します。後で保留される要素内の不明IDも隠しません。
2. 選択された候補からlinked fieldのcell/labels/axisを取り出します。unlabelledは根拠を検査して空labels/directへ明示変換します。
3. groupsのparent/readingを各valueへ展開します。既存の列・行別の意味生成と一意なtargetPathを保持します。
4. 明示的に同じ役割を複数要素で使用することと、別役割の矛盾を分けます。都合のよい方だけを残す補正はしません。
5. visual.v3に変換後、現在の`isolate_answer`、`validate_visual_graph`、`compile_visual_proposal`を通します。候補の変更・保護されたfacetの変更・別page・期限切れsnapshotは公開前にも拒否します。
6. unlabelledの根拠は消さず、検証後の該当EditUnit.detailsへ付けます。根拠のセルはreadSetに入り、反映までの手動変更で競合を検出します。根拠が同じ単位の書込対象にもなる場合は依存単位を統合します。

カタログのpolicy・生成条件・candidate digest、form schema/instructionsのdigest、推論量を解析snapshotへ固定します。payloadを返した後に最新カタログへ差し替えません。現在のplan_snapshotによるplannedCalls、共有台帳予約、二重実行防止、取消、revision保護は維持します。

この工程では1作業単位1要求を維持します。モデル応答の途中のJSONや単独の名前だけを公開しません。既存の独立作業単位は、完成応答の検証後に順次表示します。短縮後も5秒に届かなければ、依存関係を閉じた要求分割を次の修正として設計し、最初の1セルだけでページ全体の速度を代用しません。
