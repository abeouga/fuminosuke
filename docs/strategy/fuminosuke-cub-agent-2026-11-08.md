## 2. 前提：エージェントの型は「ループを誰が回すか」で分かれる

エージェントとは、LLMが次の行動（どの道具を呼ぶか）を自分で決め、プログラムが実行して結果を返し、それを繰り返す仕組み。ローカルLLMかAPIかは関係ない。人が決めた順番で推論を固定的につなぐだけなら「ワークフロー」と呼ぶ方が正確。

| ループを回す主体 | OpenAI | Claude（Anthropic） | 向いている場面 |
|---|---|---|---|
| 自分のコード | Responses API | Messages API（ツール使用） | 道具が少ない、画面や根拠表示を細かく制御したい |
| ライブラリ（自分のサーバー内） | Agents SDK | Claude Agent SDK（Claude Codeと同じ仕組み） | 道具が多い、ファイル操作やコマンド実行が中心 |
| 提供元のクラウド | Agents API（ベータ） | Claude Managed Agents（ベータ） | 長時間・非同期で動く処理 |

- 参考：https://platform.claude.com/docs/en/managed-agents/

### [訂正] 今の文之助のAIの呼び出し方

元のメモでは「文之助はClaudeのMessages APIで自前ループを回している」としていたが、コードを確かめると違った。

| 機能 | 実際の仕組み | ループか |
|---|---|---|
| 音声・文字での編集（テンプレート作成を含む） | まずOpenAIのDecisionsで、決まった選択肢から選ばせる。複雑な指示のときだけ、Responses形式で関数 `submit_edit_plan` を1回だけ強制して呼ぶ（`backend/app/editing/infrastructure/planner_provider.py`）。このResponsesは、橋渡しの処理（`backend/app/ai/claude_bridge.py`）がClaudeのMessages APIに置き換えて答えさせる | ループではない（1往復） |
| チャットの質問応答 | AIは書類・欄・計算の種類をDecisionsで選ぶだけで、値の取り出し・計算・回答の文はサーバーが作る（`backend/app/structured/qa.py`） | ループではない |
| 道具を繰り返し呼ぶ仕組み | 古いアシスタント（`backend/app/assistant/conversation.py`、OpenAI向け）にはあった。新しい編集の仕組みを有効にすると使われない | 古い経路にだけある |

つまり、文之助は「AIには有限の選択肢から選ばせ、値はサーバーが扱う」設計。まとめ役のツール使用ループは、**これから新しく書くもの**になる。

## 3. 全体構成 [提案]

```
ユーザーの質問
    ↓
まとめ役（親エージェント：Messages APIのツール使用で、自分のコードがループを回す）
    ├─ 道具1 文之助の帳票検索   → 値＋書類＋欄＋画像上の枠
    └─ 道具2 カブロガーの区間検索 → 値＋走行＋時刻・座標
    ↓
根拠付きの回答 ＋ 画面で根拠の場所を強調
```

- まとめ役：質問を受けて、どちらの道具を使うか判断し、結果を合わせて根拠付きで答える。
- 判断はまとめ役に集める。部品側はエージェントにせず「検索して根拠を返す関数」にする。
- **[提案]** 部品の道具の中ではAIを呼ばない（§5-2）。

## 4. 親エージェントの実装方式 [提案]

**Messages APIのツール使用で、ループを自分で書く方式**を推す。理由：

1. 道具が2つなら、ループは短く書ける。早く作れる。
2. 子（文之助のチャット部分）ごと呼ぶと「エージェントの中にエージェント」になり、費用・遅さ・デバッグの難しさが増える。
3. Agent SDKは中身がClaude Codeの仕組みで、ファイル操作やコマンド実行向き。Webチャットで2つの検索を使い分けるだけならその機能は使わない。
4. Managed Agentsは長時間の非同期処理向けで、今回は過剰。

- **[訂正]** 元のメモの「文之助で既に同じ仕組みを書いているので、道具を2つ並べるだけで済む」は削除した。文之助の今の仕組みはループではない（§2）。ただし、AnthropicのSDKの使い方・費用の数え方・失敗時の扱いは、文之助の橋渡しの処理（`claude_bridge.py`）が参考になる。

乗り換えを考えるタイミング：道具が大きく増えてループ管理（履歴、再試行、権限確認）が重くなったら Agent SDK を検討。

## 5. 部品の設計 [提案]

### 5-1. 共通の根拠形式 [訂正]

両方の部品が返す根拠を「種類・出典ID・位置・値」の4つに統一する。ここが揃えば、統合はほぼ配線だけになる。

元のメモの文之助の位置は `{ "sheet", "cell" }`（Excelのセル）だったが、文之助の書類の多くは写真で、Excelのセル番地を持たない。実際に持っているのは、書類ID・欄ID・欄名・ページ・画像上の枠（box）・切り抜き画像のURL。そこで `location` の中身は `kind` ごとに変えてよいことにする。

```json
{
  "kind": "document",
  "source_id": "文之助の書類ID（jobId）",
  "label": "繁殖台帳1021「はじめ」の毛色",
  "location": {
    "template_id": "テンプレートID",
    "field_id": "欄ID",
    "field_label": "欄名",
    "section": "見出し（あれば）",
    "table_id": "表ID（表の欄のとき）",
    "row_number": 1,
    "column_id": "列ID（表の欄のとき）",
    "page_id": "ページID（複数ページのとき）",
    "box": { "x": 120, "y": 340, "width": 80, "height": 30 },
    "crop_url": "欄の切り抜き画像のURL",
    "image_url": "ページ画像のURL"
  },
  "value": "黒"
}
```

```json
{
  "kind": "ride",
  "source_id": "走行ID",
  "label": "11/2 家→歯医者 区間12",
  "location": {
    "segment_id": "区間ID",
    "start": "開始時刻",
    "end": "終了時刻",
    "start_latlon": [0.0, 0.0],
    "end_latlon": [0.0, 0.0]
  },
  "value": { "vibration_mean": 0.0, "vibration_max": 0.0, "speed": 0.0 }
}
```

- 文之助の値は、今の構造化の書類（`GET /api/v2/structured/documents/{id}` の `fields[]`）の `fieldId`・`label`・`section`・`tableId`・`rowNumber`・`columnId`・`pageId`・`box`・`cropUrl`・`value` から作れる。
- 形をそろえる変換は、まとめ役の側で行う。文之助のAPIの形は変えない。
- 画像上の枠（box）は、位置合わせ済みのページ画像の画素の位置。画面ではページ画像の上に枠を描けばよい。

### 5-2. 道具1：文之助の帳票検索 [訂正]

- 使うのは、確定済みの書類を読むAPI（AIを呼ばない）：
  - `GET /api/v2/structured/documents`（一覧。`templateId`・`q`（書類名・識別値の検索）で絞れる）
  - `GET /api/v2/structured/documents/{jobId}`（1件の値・表・根拠）
- これらは確定済みの書類だけを返す。確定前の読み取り値はまとめ役に渡さない。
- 手元で動いている文之助のサーバー（`http://127.0.0.1:8010`）へ、同じPCから呼べば今のままで受け付ける（手元からの呼び出しの確認を通る）。文之助側の変更は要らない。
- **[訂正]** チャットの質問API（`POST /api/v2/structured/questions`）は道具にしない。中でAIが動くため「エージェントの中にエージェント」になる。
- 絞り込み・合計・件数などの計算は、まとめ役の道具の中のコードで行う（AIに足し算させない）。
- 返すもの：§5-1 の document 形式の根拠の一覧。

### 5-3. 道具2：カブロガーの区間検索

- 生ログをそのままAIに渡さず、「区間まとめ表」に変換してから検索させる。
- 区間（例：5秒ごと）ごとに持たせる項目：開始・終了時刻、始点・終点の座標、振動の強さ（平均）、振動の最大値、速度。
- GPSが取れなかった郊外走行は座標を空欄にして、時刻だけで引用できるようにする。
- 道具の機能：期間・場所・振動の大きさで区間を絞り込み、まとめ行を返す。回答には必ず区間IDを付けさせる。

### 5-4. 道具の定義の例（Messages APIに渡す形）[訂正]

文之助側の道具を「AIを使わない検索」に合わせて直した。

```json
[
  {
    "name": "search_ledger",
    "description": "文之助で確定済みの帳票を探し、欄の値を書類ID・欄・画像上の位置付きで返す。確定前の書類は返さない。",
    "input_schema": {
      "type": "object",
      "properties": {
        "template": { "type": "string", "description": "書類の種類の名前（例：繁殖台帳1021）。任意" },
        "document": { "type": "string", "description": "書類名や識別値（例：はじめ、耳標番号）。任意" },
        "fields": { "type": "array", "items": { "type": "string" }, "description": "欲しい欄の名前（例：毛色、価格）。任意" },
        "date_from": { "type": "string", "description": "確定日の範囲の始め（YYYY-MM-DD）。任意" },
        "date_to": { "type": "string", "description": "確定日の範囲の終わり（YYYY-MM-DD）。任意" }
      }
    }
  },
  {
    "name": "aggregate_ledger",
    "description": "文之助で確定済みの帳票の数値の欄を、サーバー側で合計・平均・件数・最大・最小する。計算に使った欄の根拠も返す。",
    "input_schema": {
      "type": "object",
      "properties": {
        "template": { "type": "string" },
        "document": { "type": "string" },
        "field": { "type": "string", "description": "計算する欄（又は表の列）の名前" },
        "operation": { "type": "string", "enum": ["sum", "avg", "count", "max", "min"] }
      },
      "required": ["field", "operation"]
    }
  },
  {
    "name": "search_ride_segments",
    "description": "カブの走行ログを区間単位で絞り込み、区間ID・時刻・座標・振動・速度を返す",
    "input_schema": {
      "type": "object",
      "properties": {
        "date_from": { "type": "string" },
        "date_to": { "type": "string" },
        "min_vibration": { "type": "number" },
        "area": { "type": "string", "description": "場所の手がかり（任意）" }
      }
    }
  }
]
```

- 項目名・引数は例。欄名の照合（表記ゆれ）は、最初は「欄名に含まれるか」の単純な一致で始める。
- `aggregate_ledger` は時間がなければ後回しでよい（`search_ledger` の結果をまとめ役が読むだけでも動く。ただし数字の計算はAIにさせない方針なので、合計を聞かれる例を見せるなら必要）。

## 6. 画面 [提案]

- **[提案]** 文之助のチャット画面には載せず、新しい1画面を作る。文之助のチャットは質問応答の専用の流れ（§2）で作られており、載せると文之助の中身に手を入れることになるため。左に会話、右に根拠を出す。
- 根拠の「種類」を見て表示を出し分ける。
  - document → 右に元書類のページ画像を出し、`box` の位置に枠を描いて強調（文之助のライブラリやチャットと同じ考え方）
  - ride → 右に地図とグラフを出し、該当区間の道筋を色付け、グラフの該当時間帯を強調
- 地図は最初は無料のOpenStreetMap系（Leaflet）で十分（Googleマップは利用キーと課金設定が必要）。
- 画像は文之助のサーバーから取る（ページ画像・切り抜きのURL）。新しい画面が別のポートで動く場合は、文之助のサーバーへの中継（まとめ役のサーバー経由）で取ると、文之助側の設定を変えずに済む。

## 7. 横断の質問を成立させる [提案]

今のままだと「帳票の質問」と「走行の質問」が別々に答えられるだけ。両方を使う質問の例：

- カブの整備・給油記録を紙に書き、文之助で読む
- 「オイル交換の後で振動は変わった？」のように、紙の記録とセンサーデータを突き合わせる

これは「記録とデータを横断して根拠を示す」形で、設備の保全に使うAIエージェント（RAG）でよく求められるものと重なる。

- **[提案]** 最初の範囲では、時間が余ったときだけにする。整備記録のテンプレートを作り、読み取り・確定するところまで要るため。
- **[提案]** やる場合も「振動の平均がこう変わった」という事実を示すところまでにし、良くなった・悪くなった・故障の兆しといった判断はさせない（走行ログは健康な走行だけのため）。
