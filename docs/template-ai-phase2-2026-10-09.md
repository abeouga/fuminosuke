# AIテンプレート作成：フェーズ2 最小比較実験

2026-10-09。対象は利用者指定の `llm-ocr-deploy`。APIモデルは全送信で `gpt-6-luna`。製品コード・通常設定・編集機能の有効化・業務データは変更していない。実APIは40送信、共有台帳は182→222/496、残274。フェーズ2の測定を完了し、次のフェーズ3（Astra / XHigh：方式決定・API設計）で停止境界を置く。

## 1. 結論

**今回の「全セルのDecisions判定 → Responses補完」という直列構成を既定方式として採用する条件は満たさなかった。** 主要比較の全体完了中央値はResponses単独12.672秒、ハイブリッド16.987秒。ハイブリッドは34.1％遅く、当初の20％短縮目標へ到達していない。固定評価帳票だけでも10.978秒対11.160秒で、短縮していない。

種類判定だけは167セル1.687秒、185セル2.096秒だった。全体の意味付けが同じ速さで完了したという結果ではない。種類の先行表示・限定範囲の判断にDecisionsを使う余地はあるが、信頼度だけで自動適用できる精度は確認していない。

両方式とも親見出し・繰り返し構造・未解決箇所の扱いに欠落があり、この評価器の提案を直接保存する実装へ進まない。Responsesは比較の基準として残し、採用方式・共通提案形式・正規化・完全性検証をフェーズ3で確定する。

## 2. 入力・測定条件

[フェーズ1](template-ai-phase1-2026-10-09.md)の5帳票を使用。3帳票は調整用、H1/H2は固定評価用。全459セルのうち役割88セル・結合39件・行7件だけが画像照合済みの重点期待値。T3/H2は既存の合成帳票。独立した人間の二重評価、全セル精度、未知帳票への一般化を証明する試験ではない。

APIへ送ったのは同一の固定画像（detail=high）、セルID・座標・text・shape等。保存role、relations、mapping、期待値、元ファイルパスは送信していない。候補はroleに依存しない座標とtextから作った近傍10件。重点39結合の必要見出しは全て候補集合内にあった。これは未採点セルの候補網羅性を保証しない。

- Responses：low、構造化JSON、最大出力24576token、store=false。
- ハイブリッド：セルごとに「種類＋主見出し」の選択をDecisionsで一括判定。返却confidenceが0.70以上の種類を先行分類として保持し、未採択セルと意味名・親・行列をResponsesで補完。
- 1試行は直列実行。反復ごとに方式の順序を反転。新しいHTTP接続・予算予約・画像準備・検証を含む総時間と、HTTP時間・先行判定時間を別に保存。
- 主要比較は5帳票×2方式×2反復＝20試行。T1/T2の第3反復4試行は補助結果。数回の測定からp95や本番速度を推定しない。cache usage・個々の値を保存した。
- 自動再試行なし。モデル名・入力・候補・schema・protocolを固定し、固定評価帳票の結果に合わせたprompt調整をしていない。

## 3. 初回の不成功と40送信の内訳

最初のResponsesはrole別ID配列にセルIDの重複があり、提案全体を拒否した。最初のDecisionsは334質問を送り、実APIが `array_above_max_length` / maximum 200として拒否した。公式参照で質問数上限を事前確定できなかったため、実応答を制約の根拠として保存した。両方の失敗をAPI利用枠に計上した。

修正したのは評価器の要求・応答形式。1セル1質問の組み合わせ候補にして最大185質問へ収め、ResponsesのrolesはセルIDを必須keyにしたobjectへ変更。ID欠落と重複keyを検査する。製品の保存仕様は変更していない。

| --- | ---: |
| 最初の不成功（Responses＋Decisions） | 2 |
| 主要比較20試行（Responses10、ハイブリッド10×2） | 30 |
| T1/T2の第3反復（各方式） | 6 |
| 調整用T1/T2の種類だけのDecisions診断 | 2 |

初期計画のH1第3反復は、上限内で診断枠を確保するため実施していない。主要比較では全5帳票を両方式2回ずつ評価し、一方だけ反復を追加した比較にはしていない。最初の形式を `prototype-v1`、初期採点を `analysis-direct-only.json` に保持した。失敗結果の削除、都合のよいfixture変更、再送の未計上はしていない。

HTTP成功は39/40。主比較の提案構造チェックは両方式とも9/10。HTTP成功・構造チェック通過・意味の正しさは別の指標である。

厳密結合はlabel集合と最寄りparentのIDを期待値と照合する。単に意味が近い文字列があるかを採点していない。印刷タイトルをparentに入れた案、親見出しをlabel集合へ入れた案は、固定した階層表現と一致しなかった。

また、T2のResponses初回は明示bindingsを省略し、列IDと行配列で対応を表していた。bindingsだけの最初の採点はこの表現を数えていなかったため、**元の直接結合一致4/78対14/78を保持したうえで**、goldを参照しない表の展開（列と同じ長さの各行をzip）を補助的に評価した。その結果が25/78対14/78。親階層の差や不正提案を正解扱いへ変更したわけではない。この二重表現自体が、次工程の提案APIで正規化すべき課題である。

未解決合計は、宣言された未解決・unknown・結合欠落・role矛盾のunion。構造チェック失敗時は当該帳票の全セルを未解決として計上する。返却された未解決配列が空という理由だけで完成扱いにしない。

## 5. 不成功・欠落の具体例

- ハイブリッドT2第2反復：未採点の下段表で `cell_0180` を2回配置。全提案を拒否した。上段の重点表が読めたことを帳票全体の受入成功とは扱わない。
- Responses H1第2反復：入力セルの結合で自身をlabel/parentに使用。全提案を拒否した。
- T1等：印刷タイトルを親にしたり、最寄りグループをlabelへ混在させたりした。roleと結合の整合性も別途必要。
- T2：正しい列・行を返す試行と、後続行を未解決にする試行があった。種類が正しいだけでは表の意味付けは完成しない。
- 一部提案はJSON schemaを満たしながら、必要な結合を未解決としても明示しなかった。schema成功だけを保存可能判定にしてはいけない。

通常のテンプレートやOCR結果への適用は一度もしていない。これらは評価器の提案生成結果であり、業務データの破損ではない。

## 6. 種類だけの診断と設計上の含意

| 帳票 | 種類判定時間 | 0.70以上の採択セル（全セル） | 重点役割一致 |
| --- | ---: | ---: | ---: |
| T1・167セル | 1.687秒 | 128/167 | 11/14 |
| T2・185セル | 2.096秒 | 138/185 | 29/29 |

T1では重点14セル全てが閾値を越えたが3セルが不一致だった。数値のconfidenceを正解確率として保証しない。2帳票1回ずつの調整用診断であり、固定評価・全体意味付け時間の結果ではない。

種類＋見出しを同じchoiceにすると、同じ種類の確率が複数見出し候補へ分散した。主比較ではT1の採択15/167、T2は6/185に留まった。保存応答の確率を種類別に合算する後分析では採択数は増えたが、誤分類を解決したわけではない。これを追加の実運用成功として数えない。

入力usageもT1の組み合わせ選択224936tokenに対し、種類だけ56287tokenだった。返答を組み合わせ候補で細分化することが無条件に効率的とは言えない。費用は実usageを根拠に別途算出できるが、ここでは金額や本番負荷を推定しない。

次工程で検討する候補は、種類判定と関連判定の分離、既存の空間解析で決まる表構造の利用、曖昧な範囲だけのAI補完、先行プレビューと全体完了の分離である。全セル・全関係を常に二つのAPIへ直列送信する方式へ固定しない。200質問を越える場合の分割と予算も仕様化する。

## 7. 成果物・検証・保持

成果物は全て `D:/llm-ocr-archive/template-ai/20261009-phase2`。

- `before.json`、`backup`：開始時ソースhash、業務ファイルhash、DB全テーブルの論理hash、DB退避。
- `manifest.json`、`inputs`、`protocol.json`：入力・候補・方式・反復の固定。元goldへのパスは採点専用で、API要求には使用しない。
- `benchmark.py`、`offline-results.json`：画像/入力SHA、許可キー、schema、候補数、ID欠落・不明ID拒否、拒否/unknown応答の処理をオフライン検証。
- `requests`、`raw`、`sends.json`、`runs.json`：要求、実応答、実送信と時間。要求ファイルの画像base64は固定画像への参照表示に置換し、実要求全体のSHAを保存。認証headerは保存しない。
- `analysis.json`、`scores`：全試行と重点期待値の照合、直接結合と表展開、完全性監査。
- `role-ablation-*`：種類だけの追加2送信と、種類別確率の後分析。
- `validation-failure-*`：不成功の保存応答から再現したtrace・重複セル。
- `after.json`、`preservation.json`：開始終了の保持照合。
- `result-validation.json`：40送信と台帳増分、全24試行の構造チェック結果の保存応答からの再生、採点母数・期待値SHA・文書参照を検証。

実行：deployの既存Pythonで外部 `benchmark.py prepare` → `offline` → `run`。初回不成功後に評価器v2の `offline` → `run`、`role_ablation.py offline` → `run` → `analyze`、`analyze.py`、`preservation.py`、`git diff --check`。固定実験の再実行は予算を新たに消費するため、単なる結果閲覧には `analysis.json` または保存応答を使う。

製品コード変更なし。両DBのschemaとdeployの業務36テーブルは保持し、既存台帳行も保持した。deployのAPI台帳に40予約だけ追加（HTTP応答39、HTTPエラー1）。root側DBは全37テーブルを保持。root18827ファイルとdeploy867ファイルのSHAが一致。deployの残る1ファイルは稼働サーバーのhealth GETが追記された `logs/dev-backend.out.log` で、差分を `runtime-log-change.json` に記録した。ログ変化を業務ファイル変化と混同せず、全868ファイル不変とは報告しない。既存OCR contractを維持した。Gitのstage/commit/push、通常DB移行・有効化、起動・停止は行っていない。

保持検証側では、rootにAPI台帳があるとの誤った前提と、稼働ログを業務ファイルと同じ扱いにした分類不足を修正した。既存の期待値や製品データを変更して通過させていない。最終の照合では明示したログ1件以外のファイル差分、業務テーブル差分、未計上の台帳追加を拒否する。

実音声、frontend build/実画面、通常保存API、OCR実行、全体unit/E2Eは今回実施していない。製品コードを変更していないため、製品実装の受入成功とは報告しない。

## 8. 次フェーズへの引き継ぎ

次は当初計画どおり **フェーズ3：方式決定・API設計、Astra / XHigh**。

1. 当初の採用規則（安全性、固定評価の誤提案/未解決、20％短縮）に照らして、既定経路とDecisionsを使う範囲を決める。
2. role、heading階層、label集合、表の行列を一つの正規化規則で表す。bindingsとtablesを矛盾する第二の正本にしない。
3. 役割全数、入力欄の結合又は未解決、自己参照・重複・role矛盾、範囲・revisionを保存前の必須検査にする。
4. 提案の先行表示・進捗・再解析・手動修正の保持・遅い応答の破棄を、既存authoring・共通22操作・receipt/undoへ接続する仕様として確定する。
5. 重大な仕様変更が必要なら実装開始前に報告する。今回は製品実装へ進まず、実測と未達条件を引き継ぐ。
