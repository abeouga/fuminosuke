## 4. 次の方式の比較判断

評価順は、正しい対応関係、品質付き応答時間、実装と運用の保守性、API量とする。

| 方式 | 利点 | 費用・失敗条件 | 今回の判断 |
| --- | --- | --- | --- |
| v5のprompt・出力をさらに短くする | 既存試作の変更が少ない | 相互依存する生成判断が残る。noneで品質が低下した実測あり | 主方針にしない |
| geometry・名称規則だけで意味まで決定 | AI待ち時間を省ける | 同形のform/records、親、記号用途を誤認すると自動誤結合になる | 意味の自動採用には使わない |
| 整合する有限の案を作り、Lunaが選択 | 参照・行展開・依存設定をモデル出力から除ける | 正解案を作れない／候補爆発／曖昧な案の誤選択が起こり得る | 次のAPI0成立性検証に選ぶ |

Phase18の「新規意味付けをResponses一回にまとめる」を、次の試作では一律の既定にしない。候補で表現できる範囲はDecisions、自由な名前や候補外の構造はResponsesまたは手動補完とする。**Decisionsを毎回Responsesの前に追加する構成にはしない。**

Decisionsは画像とテキストを入力し、固定候補の選択を返せる。独立する質問はまとめられるが、前の回答に依存する質問は別要求になるため、親・列用途・行識別など依存する判断は一つの整合した案として選ばせる。確率やconfidenceは正しさの証明ではなく、アプリのラベル付き例で判定条件を評価する必要がある。[OpenAI Decisions公式ガイド](https://developers.openai.com/api/docs/guides/decisions)

このAPI能力から文之助での速度を推定しない。P-noneの失敗は自由なJSON生成での結果であり、Decisions選択方式の成否とも別である。モデルは指定どおり **GPT-6 Luna**。OpenAIが推奨する要求回数・出力量の削減を設計根拠に使うが、実測前の性能保証にはしない。[遅延最適化ガイド](https://developers.openai.com/api/docs/guides/latency-optimization)

## 5. 責任分担と変更境界

| 処理 | 責任と受入境界 |
| --- | --- |
| snapshot / evidence | owner・版・page・revision・画像SHA・物理ID・全体候補・scope・手動facetを固定する。既存textの誤認識を真実へ昇格させない |
| 候補生成 | 配置と印字根拠から複数の意味仮説を作る。親・binding・列用途・行範囲・識別・mark設定を整合した単位にまとめる。geometryだけで採用しない |
| 事前検査 | 空／重複printed key、無参照mark、親循環、role・所有競合、範囲外操作など、そのsnapshotで成立しない案を除外する。除外理由も保存する |
| Luna / Decisions | 発行済み候補ID、`none_of_these`、`needs_context`のいずれかを選ぶ。新しい座標・path・ID・自由な保存操作を生成しない |
| 選択検証 | 選択集合のhash、応答漏れ・重複・未発行ID・revisionを検査する。独立回答同士にも書込み競合があれば保留し、先勝ちにしない |
| 共通compile | 選択された意味案を既存semantic commandへ変換し、manualと同じ検証・投影を通す。候補の事前検査だけで保存を許可しない |
| 表示・保存 | 検証した案を表示し「案を反映」→「確認して保存」を維持する。unknown・保留を保存DTOのignoredと別に保持する |

候補ごとに完全なlayoutを重複送信せず、共有する画像・根拠・行列を一度渡し、選択肢では意味の差分を表す。サーバー側には各選択肢の完全な操作計画を保持する。モデルへ見せない内部IDだけで選ばせることはしない。

依存する一単位あたりの試作上限を、保留2候補込み**32候補**とする。これはAPI仕様の上限ではなく、候補爆発を検出するための今回の設計上限。超過した単位はdeferredとし、正解が残ったように見せるための黙った打切りをしない。候補順と意味IDを分離し、順序変更でも同じ内容へ解決できることを要求する。

自由な名前・新しい記号語彙・未列挙構造はDecisionsの選択肢から無理に生成しない。候補不足が送信前に分かる場合は、別のResponses経路または手動補完へ振り分ける。`needs_context`を無制限の自動再試行命令にしない。fallbackの回数・時間・失敗も、将来の品質付き総時間に含める。

同じ値を手で指定した意図、既存の意味・親・読み取り設定も保護する。unknownは「未判定」、ignoredは根拠付きで「意味付け対象外」と区別する。候補不足や矛盾をunknownで隠してcoverageの分母から外さない。

表選択は任意。選択した表を優先し、未選択時の全ページcoverageを残す。音声編集の直近表・直近セル・値を保持する対話状態、短く区切る局所録音、手動矩形編集、既存のフォーカス表示要件は変更しない。矩形生成自体と、既存矩形への意味付けを分け、今回の結果を矩形検出精度の証明にはしない。

製品側の保存先は、現在の `CommandCompiler` → `MutationCore` → `TemplateAuthoringService` とmanual authoringの共通境界を前提とする。選択providerにDB更新権限を持たせない。音声plannerの文字列向けportへ画像・構造候補を押し込まず、選択用adapterを分離する。将来の統合時も、旧APIとの互換のためだけに二つの意味モデルや保存経路を維持しない。ただし、既存データの黙った再解釈・移行は行わない。

**次はフェーズ22：GPT-6.1 Sol / High、API0回。候補選択契約の具体化と、製品外の候補生成・選択検証の成立性試作。** 設計上の責任分担は本審査で定め、次段は実際にその制約で構造を表現できるかを確認する。schemaやHTTPを既存製品へ接続する段階ではない。

完了条件は次のとおり。

1. 生成側がgold、ケース名、帳票固有のセルIDや名称を参照しない。固定5scopeすべてで、32候補上限内に、重点role・実binding・行・markと手作成の意味投影に一致する案が存在する。これは候補coverageであり、AI選択精度として報告しない。
2. printed keyの空／重複、同形のform/records、異なる親、markの必要設定、所有重複について、成立しない案を選べないことを短い境界検証で確認する。正しい意味をgeometry規則だけで決めない。
3. 候補がない／上限超過／保留回答／候補順変更／未発行ID／snapshot・revision変更／同値手動変更でも、未解決と既存編集を保持する。親や値所有が競合する回答を合成して通さない。
4. 共通compiler/manualの意味投影・全ID/pathを保持し、旧30応答と採点が再現可能である。32候補が重すぎる場合は生成時間・入力量を報告し、上限を後から変えて成功扱いしない。

成立性を満たさなければ、原因を「候補欠落」「候補数」「既存契約で表せない意味」に分けて止める。実APIを使ったprompt調整や、汎用plannerの際限のない拡張へ移らない。

成立した場合のみ、後続の固定API比較計画を別途確定する。比較前に候補・prompt・閾値・採点・retry/fallbackを固定し、現方式との同条件比較、候補順序の影響、unknownと誤選択、品質付き総時間を測る。Phase20の採用基準を下げない。未見帳票と全ページ・実UI保存は別の受入であり、既知5scopeの成功で置換しない。今回、次回API枠の予約や送信は行っていない。
