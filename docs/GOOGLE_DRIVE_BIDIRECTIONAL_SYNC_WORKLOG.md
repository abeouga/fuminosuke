# Google Drive双方向同期 作業台帳

最終更新: 2026-08-31

## 1. 目的

この文書は、Google Drive双方向同期と書類ライブラリ統合について、次の情報を継続的に残すための作業台帳である。

- 何が実装済みか
- 現在どのタスクを作業しているか
- どこまで検証したか
- どのような問題が発生したか
- 次に何を実行するか
- 何をもって完了とするか

単なる予定表にはしない。作業開始時と終了時に更新し、実装・テスト・実ブラウザ確認を区別して記録する。

## 2. 更新ルール

1. 作業開始前に対象タスクの状態を`未着手`から`作業中`へ変更する。
2. 作業中に問題が発生した場合は、症状、原因、影響範囲、暫定回避策を対象タスクへ追記する。
3. コードを変更しただけでは`完了`にしない。各タスクの完了条件と検証項目をすべて満たした場合だけ`完了`にする。
4. 外部サービスを実際に操作していない場合は、`実ブラウザ未確認`または`実Drive未確認`と明記する。
5. 作業終了時に「作業履歴」へ追記する。過去の履歴は削除せず、訂正が必要な場合は新しい行で訂正する。
6. トークン、OAuthアクセストークン、APIキー、個人情報、Driveの非公開URLは記録しない。

状態は次の4種類を使用する。

| 状態 | 意味 |
|---|---|
| `未着手` | 実装または調査を開始していない |
| `作業中` | 調査、実装、検証のいずれかを実施中 |
| `保留` | 外部条件または利用者の操作待ち |
| `完了` | 完了条件を満たし、必要な検証結果を記録済み |

完了条件:

- 次の修正内容をGD-02へ記録する。

### GD-04 Drive更新後のDB保存失敗に対する補償処理

目的:

実行内容:

- 補償も失敗した場合は、部分失敗として記録し、次回同期で検出できる競合コードを返す。
- SQLiteでは必要な範囲だけ`BEGIN IMMEDIATE`を使用し、長時間のDrive通信中にDBロックを保持しない。
- DB commit失敗と補償失敗を注入できる単体テストを追加する。

主な対象:

- `backend/app/services/google_drive_service.py`
- `backend/tests/unit/test_document_library_bidirectional_sync.py`

完了条件:

- Drive成功・DB失敗時に元のDrive状態へ戻る。
- 補償失敗時は黙って成功扱いにせず、部分失敗として残る。
- 通常移動、同時移動、削除済み、複数ルートのテストが成功する。

検証結果:

- 書類移動のDrive更新失敗は、既存どおりDBを進めず再試行可能。
- Drive移動成功後のDB commit失敗では、Driveを元の親へ戻し、ローカルversionを進めないことを確認した。
- Drive移動適用後の応答消失でも、現在位置を再取得して元の親へ戻すことを確認した。

- 移動補償が失敗した場合は`DRIVE_DOCUMENT_MOVE_PARTIAL`を返し、DBを成功扱いにしないことを確認した。
- 書類名変更のDB commit失敗では、Drive名を元へ戻すことを確認した。
- 名称補償が失敗した場合は`DRIVE_DOCUMENT_RENAME_PARTIAL`を返すことを確認した。
- Google Drive同期・書類ライブラリ関連53件とRuffが成功した。

発生した問題:

### GD-07 全件同期を差分同期へ移行

目的:

- 共有ドライブ、複数ルート、trash、フォルダ移動を差分イベントで処理する。

完了条件:

- 変更がない2回目同期で全階層を再走査しない。
