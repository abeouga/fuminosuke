## 3. 製品外に実装した構成

### 候補生成・v3契約

`candidates.py` は既存矩形の座標だけから縦strip・連続した行区間・隣接列の候補を生成する。
文字・既存role・goldを候補生成へ渡さない。候補は最大32、行300・列100までの束縛済み参照とし、物理IDと元の座標を再生成しない。

`v3_contract.py` はLunaに候補・開始終了行・各列の用途・意味・読み方・局所表題を指定させる。
列用途はvalue / row_label / row_key / context / unknown。欄単位の意味付けと、見出し間の任意の階層案も別に保持する。
checklistのselectionModeはmultipleだけを許可し、provider schemaとdomain validatorを一致させた。

`expand.py` は候補指定を元のセル行列へ展開し、共通normalizer・command compilerへ渡す。
未知refは要求全拒否。不正な行範囲・列設定・値所有競合などは関係単位を保留する。保留単位の所有claimも競合検査に残す。
欠けた行や値を推測で補充しない。局所表題の不正をnullに置き換えて救済しない。上位階層が不正でも独立した表本体を評価できるが、未解決の親を正しい結合として数えない。

## 4. 残った原因

1. **H1で表と単体欄が同じ値を重複所有した。** 両反復で申込者の住所・氏名・電話欄が表とfieldsの両方に出力され、関係単位を保留した。欠落6結合の原因であり、候補を与えるだけでは所有の一意性は解決しない。
2. **T1で直接ラベルと親見出しが混同された。** 例えばAL11はAF11が直接ラベル、D11が親である期待に対し、D11とAF11を並列ラベルにし親nullを返した。枠を選べても意味階層は別の判断課題として残る。
3. **context列の分類方針がgoldと一致しない。** Dの展開器は説明列を値にしないためlabelへ導くが、H2の説明4セルはgoldではignored。2反復の8誤分類はこの決定的な方針差である。すべてをLunaの認識誤りと説明しない。goldや採点を後から変更せず、次審査で製品上の意味を検討する。
4. **B′は局所親を間違えやすい。** 不一致71結合のうち52はラベル集合一致・親不一致、15はラベル集合不一致、4は欠落。T2では局所表題cell_0004に対してページ表題cell_0001を親にしていた。schema通過は意味の正しさを保証しない。
5. **待ち時間は主にprovider応答。** Dの準備中央値12.382ms、検証41.504ms、provider11.312秒。B′は準備3.890ms、検証44.238ms、provider14.504秒。現在の測定では候補生成やcompilerの数十msを削っても5秒目標へ到達しない。

Dの不一致15結合は欠落6、ラベル集合5、親4。分類34不一致には見出しのunknown/label化、保留による値欠落、上記context方針差が含まれる。
未解決セルがB′より増えたことも保持する。重点表だけ改善した結果をページ全体の改善へ一般化しない。
診断は `diagnostics.py` と保存済み応答・採点だけで行い、比較コードや主結果を変更していない。
