# スマホ撮影写真・スマホ画面・文字拡大への対応（2026-10-18）

利用者の要望：「スマホから撮影した暗くてゆがんだ写真でも行ける柔軟さが必要だ。そしてスマホではテンプレート作成以外の機能が使えるようにしたい。そして文字を大きくした高齢者用ブラウザでもそのテンプレート作成以外の機能が正常に利用できるようにしたい(文字拡大を無効化させたい)」。途中で「破壊的変更を許可する」との指示あり。

検証は通常データの複製（`D:\llm-ocr-archive\template-ai\20261017-generic\data`）で行い、通常DBの業務データは変更していない。検証用のスクリプト・合成写真・結果は `D:\llm-ocr-archive\phone-photo-20261018` に置いた（製品外）。

## 1. 暗い・ゆがんだ・傾いた写真の位置合わせ

### 再現（変更前）

複製データの確定済みjob 4件（F01 履歴書、F02 住民票写し請求書、F06 点検表、F08 農薬記録簿）の記入済み画像から、机の上で撮ったスマホ写真（3024×4032 JPEG）を合成した。変換 M（元画像→写真）が既知なので、各欄の四隅について「元画像での位置合わせ結果を M⁻¹ と合成した正解」と「写真から求めた変換」の差（px、テンプレート座標）を全欄で測った。

| 条件 | 内容 |
| --- | --- |
| dark | 露出0.38、ノイズ、JPEG75 |
| shadow | 左側の影（60%）＋周辺減光 |
| rot8 / keystone | 8°傾き / 上辺14%縮む台形 |
| combo | 台形＋−5°＋暗い＋影＋ぼけ＋ノイズ＋JPEG72 |
| combo_strong | 台形20%＋12°＋露出0.3＋影＋ぼけ1.6＋JPEG65、紙面75% |
| closeup / closeup_cut | 紙が画面いっぱい（3°・台形）/ さらに上下が数%切れる |
| upside / sideways | 上下逆 / 横向き（90°） |

変更前は40条件中20条件が `LOW_REGISTRATION_CONFIDENCE` で失敗（影・組合せ・寄り・横向きは全帳票で失敗）。通った条件にも、影で照合スコア（ECC）が0.29〜0.39まで落ち、欄の位置が4px超ずれたもの（F02 combo 最大5.16px・9欄、F06 combo 4.53px・5欄）があった。

原因：
1. 位置合わせ（ORB・ECC・輪郭照合）が写真の明るさのむら・暗さをそのまま扱い、影で照合が崩れる。
2. 書類の輪郭検出（Canny・紙色マスク）が暗い写真で紙を見つけられない。
3. 横向きの写真はテンプレートの縦横比でしか輪郭を探さず、90°回転を扱えない。

### 変更

- `app/image_processing/photometric.py`（新規）：紙の背景（インク・罫線を閉じた低周波成分）を推定し、紙がテンプレートより20以上暗いか、むらが20以上大きいときだけ、背景で割って紙をテンプレートの白さにそろえる（`flatten_paper`）。テンプレートと同程度に白い画像（スキャン・保存画像）は**画素を変えない**。位置合わせが通った後、平坦化した写真に限り、切り抜き用の画像だけに雑音除去（ノイズ推定σ>3でNon-local means、それ以外は3×3メディアン）と、薄いインクの濃度復元（輝度だけを伸ばし、RGBを同じ倍率で掛けるのでペンの色は残る）をかける（`restore_ink`）。位置合わせ自体は濃度復元前の画像で行う（濃度復元を位置合わせ前に入れると特徴点が乱れ、F08の寄りで誤差6.6pxの受理が起きたため）。
- `app/image_processing/photo_registration.py`（新規）`register_document`：従来の向きでの輪郭正規化→（必要なら）紙の平坦化→従来どおりの `TemplateAligner` を最初に行う。平坦化した画像が不合格なら撮影したままの画像でも試す。それでも不合格なら、縦横を入れ替えた輪郭で90°/270°回転の両方を試す。すべての候補は既存と同じ受入条件（一致数・inlier比・再投影誤差・ECC・輪郭一致・局所輪郭）を通る必要があり、閾値は緩めていない。採用した回転・平坦化・試行の一覧は品質情報 `photoRegistration` に記録する。
- `app/image_processing/document_boundary.py`：輪郭検出用の縮小画像だけ、95%点が190未満なら明るさを引き伸ばす（明るい画像は不変）。
- `app/image_processing/registration.py`：失敗時に、失敗した候補のページ画像を `RegistrationFailure.normalized_rgb` で返す（失敗artifactの保存用）。
- `app/services/extraction_service.py`：上記 `register_document` を使う。`normalized` artifactは位置合わせに渡した画像（回転・平坦化後）。切り抜き・手書き分離・記号判定は、平坦化後の位置合わせ済み画像から作る。

mappingId・targetPath・sourceRegionId・保存矩形・padding・provider・model・prompt・schema・association・受付snapshotは変更していない。

### 結果（同じ合成写真での前後比較）

`scripts/harness.py`（`HARNESS_MODE=before` は HEAD のコードをコピーして実行）。結果は `results/before.json`・`results/after4.json`。

| 指標 | 変更前 | 変更後 |
| --- | --- | --- |
| 位置合わせ成功 | 20/40 | 39/40 |
| 欄の四隅の最大誤差（成功分） | 5.16px | 2.39px（F08上下逆、変更前と同じ） |
| 4pxを超える欄を含む条件 | 2（F02 combo 9欄、F06 combo 5欄） | 0 |
| 1条件の処理時間（最長） | 3.1秒 | 4.5秒 |

- 失敗は F01 combo_strong の1件だけで、`LOW_REGISTRATION_CONFIDENCE` として安全に拒否（切り抜き・送信へ進まない、失敗artifactと試行一覧を保存）。
- 変更前に通っていた20条件はすべて通った。誤差が増えたのは4件で、いずれも1.1px以下（F01上下逆 0.26→1.08、F08暗い 0.27→0.34、F08組合せ 0.45→0.65、F02上下逆 0.46→0.49）。暗い写真が平坦化されて位置合わせの入力が変わったため。
- 横向き4件はすべて「回転90」で通った。影・寄り（紙の端が切れる場合を含む）・暗い+台形+傾きの組合せも通る。

### 既存の画像が変わらないこと

複製DBの単一画像OCRジョブ14件（保存済みの入力・受付snapshot）すべてで、変更前と変更後の位置合わせ済み画像のSHA-256が一致した（`results/clean_regress.json`）。スキャン・きれいな画像では平坦化も回転試行も起きないため、従来どおりの画素で切り抜く。

### 実OCR（複製データのbackend、実送信）

`scripts/run_photo_ocr.py` で受付→OCR→結果を、同じテンプレート版・元の記入済み画像のjobと欄ごとに比較した。最終コードでの結果：

| 写真 | 欄の対応（sourceRegionId・boundingBoxが元jobと一致） | 元jobと同じ読み | 主な差 |
| --- | --- | --- | --- |
| F02 combo（暗い+台形+−5°+影+ぼけ） | 25/25 | 17/25 | 要確認3（本人確認・午前・昭）、表記差（「55年 4月 12日」等、印字を含めた読み） |
| F06 combo_strong（極端：露出0.3+台形20%+12°+ぼけ） | 182/182 | 160/182 | 要確認4（印字に近い見出し欄3・要観察）、全角／半角の差13、✓を「b」と誤読7・○を「0」1 |
| F01 sideways（横向き） | 99/99 | 91/99 | 「北」を「北部」2件、「ふりがな」の印字を含めた読み2件、免許の要確認1 |

欄の取り違え（別の欄の値が入る）は0件。文字の誤りは認識の誤りで、通常どおり確認画面で直す前提。極端な合成写真（ノイズσ≒9を3倍以上に増幅）では、✓のような細い記号の誤読が残った。

途中で、雑音除去の色の強さが大きすぎてペンの青が灰色になり、F02で7欄が空欄判定された版があった（`ocr_F02_combo_ui.txt`）。輝度だけを伸ばし色を残す現在の方式に直し、F02の要確認は3欄（濃度復元なしと同じ）になった。

通しの画面確認：スマホ幅375pxで、F02の合成写真を選択→内容確認→読み取り開始→書類の確認→要確認3欄を画面で修正・1欄を空欄に→確定→XLSX（`results/F02_phone_output.xlsx`、修正値が正しい行に入ることを確認）。位置合わせできないF01極端写真では、FAILEDと撮り直しの案内（四隅・同じ書類・手ぶれ/反射）が出ることを確認（外部送信なし）。

外部API：複製DBの台帳が595→646（51回、OCR 9ジョブ）。通常DBの台帳（598）には追記していない（親タスクの「通常DBを変えない」に従った。共有の上限1224の計算には加える必要がある）。

## 2. スマホ画面（テンプレート作成以外）

- `frontend/src/hooks/usePhoneDevice.ts`：画面幅ではなく端末（スマホのUA、または粗いポインタかつ画面の短辺600px未満）で判定する。PCの拡大表示ではテンプレート作成を隠さない。
- スマホでは、テンプレートの追加・複製・編集・削除の操作を出さず（読み取り画面のカード、ホームの「テンプレートを準備」）、何らかの経路でテンプレート作成画面が開かれた場合は「パソコンで行ってください」と案内して読み取りへ戻す（`OcrPage`）。
- 読み取りの画像選択：従来は `capture="environment"` のためスマホではカメラしか開けなかった。通常の選択（写真・ファイル）と「カメラで撮影」ボタンを分けた。撮影のコツを表示する。
- `frontend/src/components/phonePhoto.ts`：WebP、またはサーバーの上限（20MB・3000万画素・長辺8000px）を超える写真（48〜200MPモードなど）を、カメラの向きを反映したJPEG（長辺4800px）に変換してから送る。上限内のPNG/JPEGはそのまま（同じバイト列）送る。
- 位置合わせに失敗したjobでは、撮り直しのコツと「画像を選び直す」を表示する（`OcrJobProgressPanel`）。
- タップ後に :hover が残り、確認画面の「編集」ボタンが白地に白文字になる不具合を修正。

## 3. 文字拡大ブラウザ

`frontend/src/mobile.css`（新規、main.tsx で最後に読み込む）：

- `text-size-adjust: 100%`（-webkit-/-moz- を含む）で、Android Chrome・iOS Safari の自動文字拡大（font boosting）を無効化。
- `html { font-size: 16px }` でrem基準を固定し、ブラウザ・OSの「既定の文字サイズ」変更でレイアウトが変わらないようにした（画面の文字はほぼpx指定）。
- ページからは無効化できない設定（PCの最小フォントサイズ、Android Chromeのページ全体の拡大、iOSの表示倍率）は、崩れない設計で吸収する：1列gridの `minmax(0,1fr)` 化（280pxのカード最小幅などで画面より広がる問題）、入力欄の最大幅、ナビの折返し、狭い幅での余白縮小、確認画面の範囲選択の折返し。

確認（Browser pane、複製データ）：375px（スマホ）と、文字拡大の模擬として幅250px（375pxで150%拡大相当）＋全要素の最小文字18pxで、ホーム・読み取り（テンプレート選択・画像の準備）・書類の確認・結果の確認・質問を開き、横はみ出し0を確認。frontend build、vitest 27ファイル177件成功。

## 未対応・未検証

- 実際のスマホで撮った写真では未検証（合成写真のみ）。実機のカメラは内部で雑音除去・シャープ化するため、合成のcombo_strongより条件は良いと見込むが、測っていない。
- iPhoneのHEIC：読み取り画面の選択欄はJPEG/PNG等だけを受け付けるため、iOSは送信時にJPEGへ変換する想定。実機では未確認。
- 実機のAndroid「文字の拡大」・iOS「テキストサイズ」・PCの最小フォントサイズそのものは未確認。Browser paneでの模擬（幅250px＋最小18px）で確認した。
- 失敗画面のスタックトレース表示（既存）はスマホでも出る。利用者向けには不要だが今回は変更していない。
- テンプレート作成画面はスマホでは案内のみ（要望どおり対象外）。
- 既存のpytest（位置合わせ関係）は、テストが旧リポジトリ（llm-ocr）の旧形式を読み込み、変更前から失敗・収集エラーになるため、代わりに上記の前後比較と実OCRで確認した。
