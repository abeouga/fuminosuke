# バックエンド・フロントエンド再起動オーバーレイ 要件定義書

## 1. 文書情報

- 文書名: バックエンド・フロントエンド再起動オーバーレイ 要件定義書
- 対象OS: Windows 10 / Windows 11
- 対象リリース: 初期版（MVP）および他PC対応版
- 作成日: 2026-08-30
- 最終更新日: 2026-08-31
- ステータス: 他PC対応要件を追加

### 1.1 実装着手時の決定事項（2026-08-30）

実際の起動入口は `C:\Users\hanam\Desktop\llm-ocr起動スクリプト.lnk` であり、リンク先の `start.bat` は `scripts\dev.ps1` を通じてバックエンドとフロントエンドを一体で起動・監視する。一方だけが終了すると、既存スクリプトが他方も停止する。

この構造と競合させないため、初期実装は次の範囲に限定する。

- 両方の一括起動
- 両方の一括停止
- 両方の一括再起動
- バックエンドとフロントエンドの個別状態表示

個別起動・個別停止・個別再起動は将来要件として残すが、既存の `dev.ps1` を分離可能なプロセス管理方式へ変更するまでは実装対象外とする。

### 1.2 関連ポート一括停止（2026-08-30追加）

- 「すべてのポート」はWindows全体ではなく、設定された `llm-ocr` 開発ポート範囲を意味する。
- 既定範囲はフロントエンド `5173～5193`、バックエンド `8000～8020` とする。
- 通常の停止は `llm-ocr` のプロセス停止後、標準ポート `5173`・`8000` に残った所有プロセスも停止する。
- 起動前に標準ポート `5173`・`8000` の残留所有プロセスを停止し、ポート競合による起動失敗を防ぐ。
- 関連ポート一括停止はプロジェクト照合を行わず、設定範囲内で待受中の所有プロセスをすべて停止する。
- PID 0～4のWindows保護対象プロセスは停止せず、操作失敗として通知する。
- 実行前に対象範囲を表示し、確認を求める。

## 2. 目的

バックエンドおよびフロントエンドのコード変更後に、各プロセスを手作業で停止・再起動する操作を削減する。

Windowsデスクトップ上に常時アクセス可能な小型オーバーレイを表示し、次の操作を1回のクリックで実行できるようにする。

- バックエンドのみ再起動する
- フロントエンドのみ再起動する
- バックエンドとフロントエンドをまとめて再起動する
- 両方を起動する
- 両方を停止する

## 3. 前提と用語

### 3.1 前提

- 「Windowsのオーバーレイ」は、Xbox Game Bar拡張ではなく、通常のデスクトップ上に常時最前面表示できる小型ウィンドウを指す。
- バックエンドとフロントエンドには、それぞれ既存または作成中の起動スクリプトが存在する。
- 初期版は単一ユーザー、単一プロジェクトを対象とする。
- 実行対象はローカルPC上の開発用プロセスに限定する。
- 起動コマンド、停止方法、作業ディレクトリはアプリ本体へ固定せず、設定ファイルから指定する。

### 3.2 用語

- **起動**: 対象プロセスが停止中の場合に、新しいプロセスを開始すること。
- **停止**: 本オーバーレイが起動した対象プロセスと、その配下のプロセスを終了すること。
- **再起動**: 停止完了を確認した後、新しいプロセスを開始すること。
- **稼働中**: 対象プロセスが存在し、終了していない状態。
- **異常**: 起動失敗、想定外終了、停止タイムアウト、設定不備のいずれかが発生した状態。

## 4. 対象範囲

### 4.1 初期版に含める機能

- 常時最前面の小型操作パネル
- バックエンドとフロントエンドの個別起動、停止、再起動
- 両プロセスの一括起動、停止、再起動
- 各プロセスの状態表示
- 実行中、成功、失敗の通知
- 直近の実行ログ表示
- 設定ファイルによるコマンド、作業ディレクトリ、待機時間の指定
- 多重起動防止
- オーバーレイ位置の保存と復元
- タスクトレイからの表示切替と終了

### 4.2 初期版に含めない機能

- ソースコード変更の自動監視と自動再起動
- 複数プロジェクトの切替
- リモートサーバー、Dockerホスト、WSL内プロセスの直接管理
- Windowsサービスの管理
- 管理者権限を必要とするプロセスの制御
- 外部ネットワークからの操作
- Xbox Game Bar専用ウィジェット
- 本番環境へのデプロイや再起動

## 5. 利用者と利用条件

### 5.1 想定利用者

- Windows上でバックエンドとフロントエンドを同時に開発する開発者
- コマンドプロンプトやPowerShellで既存の起動スクリプトを実行できる利用者

### 5.2 利用開始条件

- 設定ファイルに次の内容が登録されていること。
  - バックエンドの作業ディレクトリ
  - バックエンドの起動コマンド
  - フロントエンドの作業ディレクトリ
  - フロントエンドの起動コマンド
- 各起動コマンドがオーバーレイを使用せず単独で正常に動作すること。

## 6. 主要ユースケース

### UC-01 両方を起動する

1. 利用者が「すべて起動」を押す。
2. システムはバックエンドとフロントエンドが停止中であることを確認する。
3. システムは両プロセスを開始する。
4. システムは各状態を「起動中」から「稼働中」へ更新する。
5. いずれかが失敗した場合、成功した側は原則として継続し、失敗した側と理由を表示する。

### UC-02 両方を再起動する

1. 利用者が「すべて再起動」を押す。
2. システムは二重操作を防ぐため、実行中の操作ボタンを一時的に無効化する。
3. システムは管理対象の両プロセスへ終了要求を送る。
4. 終了を確認できない場合は、設定された待機時間後に強制終了する。
5. 両方の停止を確認した後、バックエンド、フロントエンドの順に起動する。
6. 各結果を状態表示とログへ反映する。

### UC-03 片方のみ再起動する

1. 利用者が対象行の「再起動」を押す。
2. システムは選択された側だけを停止して再起動する。
3. 選択されていない側のプロセスには操作を行わない。

### UC-04 ログを確認する

1. 利用者が「ログ」を開く。
2. システムはバックエンド、フロントエンド、オーバーレイ自身の直近ログを区別して表示する。
3. 利用者はログをコピーできる。

### UC-05 オーバーレイを一時的に隠す

1. 利用者が折りたたみ操作またはタスクトレイの「非表示」を選択する。
2. オーバーレイは非表示になるが、管理中のバックエンドとフロントエンドは停止しない。
3. タスクトレイから再表示できる。

### 7.6 設定

初期版は、設定画面ではなくローカル設定ファイルによる管理を許容する。

| 設定項目 | 必須 | 説明 |
|---|---:|---|
| backend.workingDirectory | はい | バックエンドの作業ディレクトリ |
| backend.startCommand | はい | バックエンドの起動コマンドまたはスクリプト |
| frontend.workingDirectory | はい | フロントエンドの作業ディレクトリ |
| frontend.startCommand | はい | フロントエンドの起動コマンドまたはスクリプト |
| shutdownTimeoutSeconds | いいえ | 正常終了から強制終了へ切り替えるまでの秒数。初期値10秒 |

| restartOrder | いいえ | 一括再起動時の起動順。初期値は backend → frontend |
| stopManagedProcessesOnExit | いいえ | オーバーレイ終了時に管理対象も停止するか。初期値false |
| alwaysOnTop | いいえ | 常時最前面表示。初期値true |

|---|---|---|

### 8.3 操作確認

- 起動および再起動は、開発中に頻繁に使うため確認ダイアログを表示しない。
- 「すべて停止」は誤操作の影響があるため、初期設定では短い確認操作を設ける。ただし設定で省略可能とする。
- 強制終了が必要になった場合は、結果通知とログへ明示する。

## 9. 非機能要件

### 9.1 性能

- ボタン押下後、100ミリ秒以内を目標に処理中表示へ切り替える。
- 停止・再起動時間は対象スクリプトに依存するが、オーバーレイ側の追加遅延は1秒未満を目標とする。
- 待機中や稼働監視中にCPUを継続的に高負荷にしない。
- 通常時のメモリ使用量は100MB以下を目標とする。

### 9.2 信頼性

- 操作を連打してもプロセスを多重起動しない。
- 一方の起動失敗が、もう一方の状態を誤表示させない。
- オーバーレイが異常終了しても、管理対象プロセスを無条件に強制終了しない。
- 再起動処理の各段階をログから追跡できる。

### 9.3 セキュリティ

- 任意の外部入力を起動コマンドへ連結しない。
- 設定ファイルはローカルユーザーだけが変更できる場所へ保存する。
- 管理者権限を初期要件としない。
- 本オーバーレイが起動していない無関係なプロセスを終了しない。
- ネットワーク待受ポートを設けない。

### 9.4 ユーザビリティ

- 日常操作の中心である「すべて再起動」を折りたたみ状態でも1回のクリックで実行できる。
- 主要操作は色だけでなくラベルでも識別できる。
- 失敗通知には、最低限「対象」「操作」「原因概要」「ログへの導線」を含める。
- オーバーレイが他の操作を妨げる場合、すぐ非表示または移動できる。

### 9.5 互換性・配布

- Windows 10およびWindows 11の64bit環境で動作する。
- 開発用PCへユーザー単位で配置できる。
- 初期版ではMicrosoft Store配布を必須としない。
- 自動起動は任意設定とし、既定では無効とする。

## 10. 例外・エラー処理

| 条件 | 期待動作 |
|---|---|
| 設定ファイルがない | 操作を無効化し、設定ファイルの作成場所を表示する |
| 起動スクリプトがない | 対象だけを異常状態にし、不足しているパスを表示する |
| 起動コマンドが即時終了する | 異常状態にし、終了コードと標準エラーへの導線を表示する |
| 正常終了しない | タイムアウト後に管理対象のプロセスツリーだけを強制終了し、その事実を通知する |
| 一方だけ再起動に失敗する | もう一方を自動停止せず、個別の結果を表示する |
| 操作中に同じボタンを連打する | 2回目以降を無視し、多重処理を発生させない |
| 前回PIDが別プロセスに再利用されている | 管理対象とみなさず、状態不明として再照合する |
| オーバーレイを終了する | 既定では管理中プロセスを継続する |

## 11. 受入基準

### AC-01 一括再起動

- 両方が稼働中の状態で「すべて再起動」を1回押すと、両方の旧プロセスが終了する。
- 旧プロセスの終了確認後に、新しいバックエンドとフロントエンドがそれぞれ1つだけ起動する。
- UIが「再起動中」から「稼働中」へ変化する。
- 操作日時と結果がログへ残る。

### AC-02 個別再起動

- バックエンドの「再起動」を押しても、フロントエンドのPIDが変化しない。
- フロントエンドの「再起動」を押しても、バックエンドのPIDが変化しない。

### AC-03 多重起動防止

- 「すべて再起動」を10回連続で押しても、対象ごとに稼働するプロセスは1つだけである。
- 処理中は競合するボタンが無効表示になる。

### AC-04 停止失敗

- 対象が正常終了要求へ応答しない場合、設定時間経過後に管理対象だけが強制終了される。
- 無関係な同名プロセスは終了しない。
- 強制終了した事実がUIとログに表示される。

### AC-05 起動失敗

- 存在しないスクリプトを設定した状態で起動すると、対象が「異常」と表示される。
- 他方のプロセス状態には影響しない。
- 原因を特定できるメッセージとログが表示される。

### AC-06 表示状態の保持

- オーバーレイを移動して終了し、再度起動すると、前回位置付近に表示される。
- 保存位置が存在しないモニター上になった場合は、主モニターの表示範囲内へ補正される。

### AC-07 オーバーレイ終了

- 既定設定でオーバーレイを終了しても、稼働中のバックエンドとフロントエンドは継続する。
- `stopManagedProcessesOnExit=true` の場合は、終了前に管理対象を停止する。

## 12. 実装前に確定が必要な項目

以下は、要件確定または実装着手前に実値を決定する。

1. バックエンドの作業ディレクトリと起動コマンド
2. フロントエンドの作業ディレクトリと起動コマンド
3. 起動スクリプトが生成する子プロセスの構造
4. 正常終了に使用できる方法（コンソール制御イベント、標準入力、既存停止スクリプトなど）
5. 稼働判定を「プロセス存続」だけで行うか、HTTPヘルスチェックも使用するか
6. Windowsログイン時の自動起動が必要か
7. 「すべて停止」の確認操作を残すか
8. 採用する実装技術と配布形式

## 13. 推奨する実装方針

初期版は、Windows専用の軽量デスクトップアプリとして実装する。

- UI: 常時最前面にできる枠なし小型ウィンドウ
- 常駐: タスクトレイ
- プロセス管理: 起動したプロセスのPID、開始時刻、実行ファイル情報を保持し、プロセスツリー単位で管理
- 設定: JSON等のローカル設定ファイル
- ログ: 日次または容量制限付きのローカルファイル
- 稼働判定: 初期版ではプロセス存続を必須とし、HTTPヘルスチェックは設定可能な追加判定とする

実装技術は、既存資産がない場合、Windowsとの統合、プロセス制御、配布の単純さを優先して .NET 8 + WPF または WinUI 3 を第一候補とする。Web技術で統一する事情がある場合は Tauri を代替候補とし、Electronは初期版の小型常駐ツールとしてはメモリ使用量の面で優先度を下げる。

## 14. 完了条件

初期版は、次のすべてを満たした時点で完了とする。

- 必須要件が実装されている。
- AC-01からAC-07までの受入試験がWindows 10または11の実機で合格している。
- 対象プロジェクトの実際の起動スクリプトで、一括再起動を10回連続実行して多重起動がない。
- 起動失敗、停止タイムアウト、片側だけの失敗を再現し、誤って無関係なプロセスを終了しないことを確認している。
- 設定方法、起動方法、終了方法、ログ保存先が利用手順書に記載されている。

## 15. 他PC対応版の要件

### 15.1 目的と完成状態

他PC対応版は、特定のWindowsユーザー名、デスクトップ位置、開発PC固有のショートカット、または事前導入済みの.NETランタイムに依存せず、配布パッケージを別のWindows PCへ展開して初回設定を行えば使用できる状態を目的とする。

完成状態は次のとおりとする。

1. 配布ZIPを利用者が書き込み可能な任意フォルダーへ展開できる。
2. `SysOverRay.exe` の初回起動時に設定画面が開く。
3. 利用者がプロジェクトフォルダーと起動スクリプトを選択できる。
4. 設定検証に合格した後、「起動」「停止」「再起動」「関連ポートを全停止」を利用できる。
5. PCを再起動しても設定とウィンドウ位置が保持される。
6. 配布元PCのユーザー名や絶対パスが、配布物または初期設定へ残らない。

| ID | 要件 | 優先度 |

### 15.9 他PC対応版の受入基準

#### AC-PT-01 クリーンPCへの導入

- SysOverRay未導入かつ.NET Desktop Runtime未導入のWindows 11 x64実機で試験する。
- 配布ZIPの展開後、`SysOverRay.exe` が起動する。
- 管理者権限、インストーラー、.NETの追加導入を要求しない。

#### AC-PT-02 初回設定

- 設定なしで起動すると初回設定画面が表示される。
- 任意のユーザーフォルダーに置いたプロジェクトと起動スクリプトを選択できる。
- 不正なパス、URL、ポート範囲を保存できない。
- 設定完了後に操作ボタンが有効になる。

#### AC-PT-03 実操作

- 移行先PCの実プロジェクトで「起動」を実行し、BackendとFrontendが1つずつ起動してHTTP確認に合格する。
- 「停止」で両方のLISTENポートと関連プロセスが残らない。
- 再度起動後、「関連ポートを全停止」で設定範囲内のLISTEN数が0になる。
- 実行順序は「全停止 → 起動 → 通常停止 → 起動 → 全停止」とし、全段階を実画面と実ポートで確認する。

#### AC-PT-04 設定保持と更新

- Windows再起動後も設定とウィンドウ位置が保持される。
- アプリを新版へ置き換えても利用者設定とログが保持される。
- 別PCのユーザー名または元PCのパスが画面、ログ、設定に現れない。

#### AC-PT-05 パス互換性

- 日本語と空白を含むプロジェクトパスおよび起動スクリプトで、起動・停止・全停止が成功する。
- プロジェクトがデスクトップ以外に置かれていても動作する。

### 15.10 現行版との差分と実装優先順位

現行版はこの節の要件をまだ満たしていない。確認済みの主要差分は次のとおりである。

| 優先順位 | 現行差分 | 必要な対応 |
|---:|---|---|
| 1 | `C:\Users\hanam\...` が設定ファイルとコードの既定値に含まれる | 固有既定値を削除し、未設定状態と初回設定画面を導入する |
| 2 | `--self-contained false` で配布している | `--self-contained true` の `win-x64` 配布へ変更する |
| 3 | 設定異常時にPC固有の既定値へ戻る | フォールバックを廃止し、操作を無効化して設定修正を要求する |
| 4 | 設定変更にJSONの直接編集が必要 | 初回設定および設定再編集画面を追加する |
| 5 | 更新時の設定保護手順が未定義 | ユーザー設定を実行ファイルから分離し、更新手順を定義する |
| 6 | クリーンPCでの配布試験を実施していない | AC-PT-01～05を別PCまたはクリーンVMで実施する |

他PC対応版の実装完了は、ソースのビルド成功だけでは判定しない。異なるユーザー名と異なる配置パスを持つWindows実機またはクリーンVMで、AC-PT-01～05の合格を必須とする。
